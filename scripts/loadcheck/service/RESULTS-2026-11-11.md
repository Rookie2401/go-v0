# Repository service scaling benchmark, 2026-11-11

How to run: from the repo root, `npx vite-node scripts/loadcheck/service/bench-service.ts <events>` (default 12000; no install, no network, no browser).
It builds the service in process over a real SQLite file in the OS temp directory (same wiring as `main.ts`, no rate limiter, no node:http), seeds one Albanian learner, times each route, prints one JSON line and a table, and deletes the temp database.
Statement counts come from patching `node:sqlite`'s `StatementSync` prototype (run/all/get/iterate) inside the script; times are in-process wall-clock (no network, so a real client adds transport and TLS on top).

Seed: N lookups (750 distinct words cycling, 4 minutes apart in the past, batches of 200 via POST /events), then 200 cards x (1 CardAdded + 4 CardReviewed) = 1000 events, then 5 private documents. Head = N + 1012 (+ the enrolment event).
Vocabulary stays at 749 words at both sizes, so any growth below is growth with the event log, not with the word count.

## Growth, 3000 to 12000 lookups (events x4; head x3.2)

- Linear (about 3-5x): GET /candidates after an append (57.8 to 266.6 ms, 4.6x; cold 4.8x), GET /preferences (17.9 to 59.5, 3.3x), full pull (32 to 113 ms, 3.5x; bytes 3.25 to 10.86 MB, 3.3x, 14 sequential pages).
- Worse than linear (about 9-11x): GET /vocabulary no sort (87 to 799 ms, 9.2x), sort=recent (578 to 6286 ms, 10.9x); the full walk is 4.3x only because the page count stayed 8 (749 words), but each page went from about 0.77 s to 3.3 s. The seeding itself is also superlinear: 2.7 s to 23.8 s for the lookups (8.7x), last 200-batch 159 to 1036 ms (6.5x) at constant statement count (3413), so per-statement cost grows.
- Mild growth (2-2.5x), statement count constant: GET /knowledge 60 ids (2.4x) and ALL (2.5x), POST 1 event (11.4 to 22.7 ms, 2.0x, 33 statements both times). Time rises while statements do not, so the cost is in row sizes or in-memory work, not query count.
- Flat: GET /enrolments, GET /sync/status, GET /candidates inside the 20 s window (2 to 6 ms, 4 statements). GET /me is 3.8 to 27.3 ms with 7 statements in both; treat that rise as noise-prone until rerun.
- Cache note: the candidates cache is voided by every append, so within a push-heavy session it is a miss each time.

Not measured: network and TLS cost, gzip (`maybeGzip` is in main.ts's http bridge, not in `handle`), Postgres, and a real-device sync client's own folding.

## After the vocabulary fix

Same benchmark, same seed, rerun after the change (`npx vite-node scripts/loadcheck/service/bench-service.ts 3000` and `... 12000`). Machine load differs from the first run (the 12000 seed took 39.7 s here against 25.4 s before), so compare ratios, not single numbers.

What changed: the five per-unit statements the listing calls (encounter summaries, date ranges, review status, assistance ids, the source-reference filter) now start from the page's units (`event_units` by `unit_id`, then each event by its unique id) instead of from every event of the learner; migration 005 adds `event_units (unit_id, event_id)` and `aliases (new_id)`. A sorted listing orders the vocabulary once per walk (cached by the learner's head sequence, 20 s, like the candidates) and enriches only the page it returns. Profile and plans: see `profile-vocabulary.ts` (`npx vite-node scripts/loadcheck/service/profile-vocabulary.ts 12000`).

What is still not proportional to the page alone: one page reads the events of its own 100 units (about 1,600 rows at 12000 events, 16 per unit, in four statements), so it still grows with how often those words were met; and the first sorted page of a walk reads every unit's encounter dates (about 750 rows out of 12,000 events, 70-110 ms at 12000). A stored per-unit summary (first/last encounter, last event) would remove both; not built.

## After the push, alias-stamp and pull fixes

Changes: `listEventsOfUnits` (SQLite) starts from `event_units` by unit and fetches each event by id (`CROSS JOIN`, as the vocabulary statements); the SQLite store implements `aliasStamp()` (a counter row in `service_state`, bumped inside the alias write's transaction), so the engine no longer reads all of the learner's knowledge rows on every read and projection; the sync client's pages after the first ask for `documents: false` (the server's documents-on rows below are the raw server answer, unchanged, for clients already installed); a device pull appends a page in one store call and projects once (probe: `golearn-history/probe-pull.ts`). Statement profile of a push: `npx vite-node scripts/loadcheck/service/profile-push.ts 12000`. Same machine, run after the change; machine load differs between runs, so compare ratios.
