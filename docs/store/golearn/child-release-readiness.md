# Child release readiness: data flows and implementation gaps

**Scope correction:** the owner clarified that 4+ is a proposed content-suitability rating, not a minimum account age, and does not request extra reading restrictions. The earlier assumption that a child-account product had been requested was incorrect. This document preserves the data-flow findings and optional architecture analysis; choosing or implementing either child mode below is not an approved release requirement. The actual audience and account/data practices still need accurate privacy review. This is a product implementation audit, not a legal opinion or a finding of compliance/noncompliance. Existing learner-operated switches, email confirmation and terms acceptance must not be represented as verified parental consent.

## Existing flows and where they appear in code

| Flow | Current behavior and evidence | Product control gap for an age 4–12 audience |
|---|---|---|
| Device identity and local learning history | The extension creates a persistent device ID and attributes events to `local:<deviceId>` when signed out. `src/background/recorder.ts` writes events to the local log and sync queue; events include learner, enrolment, language, event timestamp, producer/device ID, and learning actions. `src/background/core.ts` clears local events/metrics/queues on a device. | Device-only mode needs a clear adult setup boundary, no account creation/sync entry point for child mode, and simple adult-controlled export/delete. Device IDs and event records may be personal information when linked to a child/account; local-only does not eliminate data-processing concerns for online features or browser platform storage. No mode currently enforces the boundary. |
| Account creation and cloud sync | `app/screens/signin.ts` calls account creation/sign-in optional and says signing in uploads local progress and syncs across devices. `app/context.ts` passes email, password, deviceId and platform to the account client. `src/background/sync.ts` sends queued learning events and pulls account events using the session token; sync runs after queued events and on alarms/reconnection. | No parent account/child profile relationship, adult authorization, child age gate, parent dashboard, separate parental consent event, or consent revocation lock is present. Existing `terms-and-privacy` acceptance in `app/consent.ts` is generated by child-facing account creation and best-effort records an event; this is not parent verification. Child cloud sync therefore has no implementation basis to be enabled at launch. |
| Learning event contents | `src/background/recorder.ts` accepts lookup, encounter, analysis, pronunciation, marking/correction and assistance events. It replaces placeholder identity, bounds event size, hashes/limits some word payloads and keeps the local log. `src/background/sync.ts` pushes account-attributed events. `repository-contract` event schemas define event and producer metadata. | The exact payload inventory should be checked field-by-field against final production traffic and retention. Avoid sending raw page text, full URLs, or unnecessary content; confirm event IDs, timestamps, device IDs, vocabulary hashes/short word lists and derived proficiency are retained only as needed. No child-specific retention schedule or parent access/delete workflow was found in this audit. |
| Remote speech | `app/screens/privacy.ts` defaults to local-only speech and has an explicit remote speech switch. `app/consent.ts` records the switch as a learning event, but it is learner-operated. `src/background/speech.ts` sends explicitly requested text through the authenticated service; `server/speechHandler.ts` proxies synthesis to Azure Speech. | A child toggling the switch is not an adult authorization control. For child mode, keep remote speech disabled unless the adult controls the setting and the service path is covered by a reviewed consent design. Document text recipient, purpose, transient processing, provider retention/logging, and deletion constraints. Do not assume speech text is never logged without verifying service and provider behavior. |
| Translation / AI | The visible privacy screen keeps outside-AI processing disabled and not switchable. The packaged sentence-translation bridge in `src/background/translation.ts` accepts only explicit requests and a fixed loopback endpoint with a local token; the store build excludes developer `translation.local.json`. Browser translation may also be offered by platform APIs in `src/translation/provider.ts`. | Verify the exact release UI and provider selection. Do not represent all translation as local without checking browser API behavior on supported browsers. Do not add cloud translation for child profiles without an adult-controlled, provider-specific disclosure/consent path and data minimization. |
| Dictionary and language packs | `app/config.json` sets `dictionaryFallbackUrl` to the public GitHub Pages host. `src/background/gloss.ts` fetches language pack data/shards and caches pack data in extension storage; `src/lexicon/prepare.ts` loads packaged extension lexicon shards on demand. | Remote asset requests disclose ordinary network metadata to the hosting provider and identify requested asset paths; verify that lookup terms or page content are not included in requests. Provide a way to preinstall required packs for a device-only mode and avoid unique learner IDs in asset URLs. Include host/provider and logs/retention in data inventory. |
| Deletion and retention | The app has local clear/export and account deletion UX (`app/screens/privacy.ts`, `app/screens/accountSecurity.ts`, `src/background/core.ts`). Account security routes provide scheduled purge behavior through the account client. Operational information supplied for this audit says Render Oregon, Resend, and backups of seven daily plus four weekly copies. | Verify end-to-end server deletion, backup expiry, device revocation, exported data, processor logs, and parent authority before promising deletion. Child account deletion should be adult-controlled and cover synced events, derived profiles, devices, queues and backups under a disclosed schedule. |

## Two product models to decide

**Adult-supervised device-only:** adult configures the browser/device; child uses a no-account profile; no cloud sync, remote speech, external translation, or child-specific telemetry. Learning history stays in local extension storage, with adult-accessible clear/export and device-level safeguards. This reduces server-side child data flows but still needs a precise inventory of browser, static asset and operational logs, and it is not automatically a legal safe harbor. Current code has a no-account path and local-only speech defaults, but it has no enforced child mode that hides account creation, disables syncing, or requires an adult to own settings/deletion.

**Child profiles with cloud sync:** adult account owns child profiles, grants clear permissions by purpose/provider, can inspect/export/delete each child profile, revoke devices and disable individual flows. The backend must enforce adult/child authorization on every profile, sync, speech, export, deletion and device route; front-end-only controls are inadequate. This needs a consent and identity architecture before release: verifiable adult authorization appropriate to the service, auditable consent scope/version/time, parent notice/access/revocation, child profile separation, data minimization, retention/deletion including backups, and processor contracts/behavior. Existing email confirmation and learner-operated consent settings do not provide these controls.

These models were proposed before the owner's clarification and are not pending product choices. Do not implement either solely because the proposed content-suitability rating is 4+. Any future child-specific data features would need their own requirements and review; a child-entered birth date or checkbox must not be represented as verified parental consent.

## Bounded implementation work after model selection

For device-only: add an explicit adult setup/lock state; suppress account, cross-device sync and profile-transfer controls in the child profile; enforce those restrictions in background routing (not just UI); keep speech/local processing at safe defaults and prevent accidental text uploads; make adult-visible local export/clear obvious and test after restart/reinstall; add tests that child mode cannot invoke account/sync/remotes.

For cloud profiles: design server-owned guardian/child entities and authorization before UI work; implement parent verification and notice/consent records; gate profile creation and every data route server-side; add per-child access/export/delete and revocation; audit content/event payloads and provider disclosures; define retention and backup expiry. Test authorization boundaries, cross-profile isolation, revoked consent, deletion propagation and offline queues. This is a substantial product/backend project, not a listing-copy change.

## Primary reference

The FTC’s COPPA FAQ explains that covered child-directed services and services with actual knowledge of collecting personal information from children generally need notice to parents and prior verifiable parental consent, subject to limited exceptions; it also discusses service-provider collection and parent access/deletion rights. Whether and how the rule applies to this product and each data flow requires legal analysis.
