# Scale: from one 512 MB instance to everyone (2026-11-12)

The owner, 2026-11-12: "start considering an alternative for when this system is published, and 8 billion people are
hypothetically free to use it simultaneously. I know that will not happen, but I want you to see the scale we will
eventually be dealing with."

This is a first look, not a plan anyone has approved. Figures marked *measured* were measured on this repository on
2026-11-12. Everything else is an order-of-magnitude estimate meant to show where the walls are, not a price quote.

## 1. Where we are

| | today |
|---|---|
| Service | one Node process on Render, 512 MB, one region (Oregon), SQLite on one 1 GB disk |
| Memory at rest | 124 MB compiled with plain Node (*measured*), down from 345 to 361 MB under vite-node, which ran the instance out of memory ten times on 2026-11-12 |
| Peak under load | 202 MB at 6,000 events and 12 concurrent page loads (*measured*); a full vocabulary scan adds 90 to 110 MB at 20,000 events (`scripts/loadcheck/service/profile-memory.ts`) |
| One stored event | about 480 bytes of JSON; about 3.8 KB per event in the SQLite file once indexes and projected rows are counted (*measured*, 6,001 events, 23 MB file) |
| Dictionaries | static files, about 65 MB gzipped for five languages; 226 shard downloads on a first sign-in |
| Learners | a handful |

## 2. What already scales, and should be protected

These are the decisions that make "everyone" thinkable at all. Each future change should be checked against them.

1. **Everything a learner owns is keyed by the learner.** The event log, the knowledge rows, preferences, documents and
   sessions are all per learner, with a per-learner sequence. No hot path joins two learners. That is the property that
   lets the data be split across any number of machines (sharding) without redesign. The only cross-learner readers are
   offline tools (`scripts/ops/corrections.mts`, purge), which is correct.
2. **The device does most of the work.** GoLearn reads pages, looks words up and keeps its own store on the device;
   GoReview builds decks on the device. The server is mostly a place to keep and pass on events. Every piece of work
   that moves to the device is work the server never does 8 billion times.
3. **Dictionaries and language packs are static files.** They can be served by a content delivery network (CDN) from
   caches near the learner, without our servers seeing the request.
4. **Pushes are idempotent.** An event is stored once however many times a phone retries, which is what lets an
   unreliable network and many servers coexist.

## 3. The numbers at the top

Two scenarios: a very large success (800 million learners active on a given day, the size of the largest consumer apps)
and the owner's ceiling (8 billion learners).

| | 800 M daily | 8 B daily |
|---|---|---|
| Events written per day (150 per learner: lookups and reviews) | 120 billion | 1.2 trillion |
| Events per second, average / busy hour (x3) | 1.4 M / 4 M | 14 M / 40 M |
| New raw event data per day (480 B each) | about 58 TB | about 580 TB |
| The same, as SQLite holds it today (3.8 KB each) | about 450 TB | about 4.5 PB |
| Raw event data per year | about 21 PB | about 210 PB |
| First dictionary download (say 20 MB per learner, one language) | 16 PB once | 160 PB once |
| Open connections if every device holds `POST /sync/wait` open | 800 M+ | 8 B+ |

What these say:

- **Storage is the first wall, not compute.** Keeping every event forever, in the form stored today, is petabytes a day.
  Events must be compacted (an old stretch of a learner's log folded into one snapshot), compressed (JSON compresses
  about five times), moved to cheap cold storage after a while, and stored in a compact binary form rather than JSON
  with indexes on everything.
- **Delivery is the second.** Dictionary downloads alone are tens to hundreds of petabytes. They have to be cut finer
  (by language, then by how common the word is, so a learner downloads the first 20,000 words and asks for the rest one
  at a time), updated as differences rather than whole files, and carried by a CDN (or shipped inside the app).
- **Held connections are the third.** One held request per device is fine for hundreds of devices and impossible for
  billions. Phones should be told about changes by the platform's own push service (Apple, Google), and otherwise sync
  when opened.
- **Compute is manageable if no request reads a whole history.** Candidates now take about 21 ms at 12,000 events
  (stage 3 of `LOADING-ARCHITECTURE-2026-11-10.md`); 800 million learners opening the home 20 times a day at that cost is
  a few thousand processor cores, which is ordinary. A request that reads the whole log is not: at 90 to 110 MB per
  scan, it is the thing that already broke a 512 MB instance with a handful of learners.

## 4. What breaks, in the order it breaks

| Learners | What fails first | What to do then |
|---|---|---|
| tens (now) | one 512 MB instance: memory (fixed today by running compiled); the single disk is the only copy of the backups | off-site, encrypted backups (the five `BACKUP_*` settings); consider the 2 GB instance as cheap insurance |
| hundreds | one process: SQLite is synchronous, so one heavy request stalls everyone; a restart is an outage | request deadlines; move to Postgres (already supported by `repository-store`, `scripts/ops/migrate-sqlite-to-postgres.mts`) |
| thousands | needing a second process. **Two things live in one process's memory and stop working with two:** the change notifier (`notifier.ts`, held `/sync/wait`) and the rate limiter (`ratelimit.ts`). With two instances a phone would hear of a change only when its wait times out, and each limit would count only one instance's share | move both into the database or a small shared store (Redis-like); then run two or more instances behind the load balancer, so a deploy or a crash is not an outage |
| hundreds of thousands | one Postgres server; email volume; sign-in cost (scrypt is deliberately slow) | managed Postgres with replicas and point-in-time recovery; a real email provider; long-lived device sessions and passkeys so people rarely type a password |
| millions | the shared word list: every `POST /lookup` writes analysis rows into tables shared by everyone, a single hot spot | build the shared linguistic data offline as versioned packs, published as static files; the service only reads them. Learner reports stay a queue a reviewer works through |
| tens of millions | one database of any size; one region (latency, and the law) | split learners across many databases by learner id; then regional **cells** (below) |
| hundreds of millions to billions | storage, delivery and connections (section 3) | compaction and cold storage; finer dictionaries over a CDN; platform push notifications instead of held requests |

## 5. The shape at the top: cells

A **cell** is a complete, independent copy of the service for one part of the world: its own stateless servers (as many
as the load needs), its own databases holding that cell's learners, its own object storage for archives and backups,
and its own message channel for "something changed" notices. Cells share nothing, so a fault in one never reaches
another, and a cell is the unit that is added when growth needs it.

In front of the cells sit only three small global pieces:

1. **A directory**: which cell a learner lives in. Tiny (an id and a cell name) and read-mostly, so it caches everywhere.
2. **Sign-in**: one account across devices and cells. Ideally a proven identity provider rather than our own password
   table, which is the riskiest thing we hold.
3. **The linguistic build**: dictionaries, packs and the shared word list built offline and published to the CDN.
   Learner corrections arrive as reports, are reviewed, and ship in the next pack.

And under everything, the rule that already holds: **the device is the computer.** The server keeps the learner's log,
passes changes between that learner's devices, and computes nothing it could leave to the device. Deck building,
knowledge projection and lookups happen on the phone or in the browser, against packs downloaded once.

Cells also answer the law, which arrives long before the billions: data-residency rules (the EU, India, China, Russia
and others) require some learners' data to stay in their country, and a cell per jurisdiction is how large services
meet that.

## 6. What it would take, besides servers

At this scale the hard parts are not technical:

- **Money.** Storage, CDN delivery and email at these volumes run from millions to hundreds of millions of dollars a year,
  even with a lean design. A free service needs a funding model before it needs cells.
- **People.** On-call operations around the clock, security response, support, and reviewers for every language whose
  dictionary learners rely on.
- **Law and safety.** Privacy regulators in every market, children's-privacy rules (COPPA, the UK Children's Code),
  account-deletion and export at scale, and moderation duties for anything learners write and keep (GoTell documents).
- **Language quality.** Every dictionary is machine-built today and says so. Billions of learners means native-speaker
  review for every language, which is a programme, not a script.

## 7. What to do now, cheaply, so the top stays reachable

None of these needs new infrastructure; each keeps a door open.

1. Keep every new table and request keyed by learner, with no cross-learner query in a request path (a test could
   enforce this on `handler.ts`).
2. No new request that reads a whole history; the loading rule of 2026-11-10 already says this for the clients.
3. Make the service stateless: move the change notifier and the rate limiter out of process memory before a second
   instance is ever needed.
4. Keep new work on the device by default; anything new on the server should say why it cannot run on the device.
5. Version every pack and event format (already done for events: contract v3), so cells can upgrade one at a time.
6. Measure, on Render, the four numbers that predict the walls: resident memory, events per learner, bytes per event,
   and the slowest request. `/metrics` already reports the first and has what is needed for the others.
7. Set up the off-site, encrypted backups now: losing the one disk loses everyone, at any scale.
