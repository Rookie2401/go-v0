# GoReview spaced-repetition system: audit and rebuild proposal (2026-10-29)

Audited at master `2663f585` (GoReview 3 landed at `b186d7be`). Everything below was read from the code, the tests and the
docs; the timings were measured on this machine with a throwaway benchmark (not committed) over synthetic histories built the
way `test/goreview/transfer/scale-scenarios.test.ts` builds them. Nothing in the system was changed.

## 1. What the system is today

| Part | Where | What it does |
|---|---|---|
| Memory model | `packages/goreview/src/scheduler/fsrs.ts` | A thin adapter over ts-fsrs 5.4.2 (FSRS-6). Published default weights, retention 0.90 (Settings allow 0.70–0.97), fuzz off, short-term steps on (`1m`, `10m`; relearning `10m`), maximum interval 36,500 days. Every state is stamped with `algorithm` + `parametersVersion` (a hash of weights, retention, steps). |
| Deck | `scheduler/deck.ts` | A fold over the learner's immutable event log: `CardAdded` / `CardRemoved` / three review kinds / `ReviewItemInvalidated`. Each review replays under the profile recorded on it; corrections retract; concurrent offline branches are classified by the contract (`review-classification.ts`, 24-hour sibling window); duplicate ids, cycles and stale predecessors are diagnosed, never silently applied. |
| Grades | `grading/grade.ts` `ratingFor` | correct → Good (self-graded: Hard/Easy), partial → Again unless retrieval succeeded, incorrect → Again. Any assistance, hint, challenge, extra replay or shown transcript → no rating (the event is kept as evidence only). |
| Planner | `planner/planner.ts` + `priority-policy.ts`, `admission-policy.ts`, `budget.ts`, `microdeck.ts`, `eligibility.ts` | Tiers: due learning → due review → remediation → new. Inside the first two tiers the order is due time, then a priority score as tie-breaker. New cards are bounded by `maxNew`, a UTC-day budget, a workload-aware admission and the adaptive micro-deck target (10, 4–60, ±2). Time budget 10 min by default with estimated seconds per family (15–40 s). |
| Session | `session/runner.ts` | Records through the device queue before advancing; timed learning returns are inserted mid-session and displace unshown lower-priority work; deterministic event ids per position; undo as a validated correction. |
| Personalization | `server/review/optimizer.ts`, `scripts/optimize-goreview.mts`, `app/profiles.ts` | The official `@open-spaced-repetition/binding` (Node only). Gate: ≥400 delayed independent reviews, ≥50 targets, ≥60 days, 80/20 chronological hold-out, candidate must improve log loss without worsening calibration. The learner runs a CLI, then imports a JSON report in Settings. Only `written-recognition`; only applied to written-recognition cards at record time. |
| Second memory model | `packages/repository-engine/src/projection.ts` `deriveRow`/`retentionAt`, `candidates.ts` | The Repository keeps its own retention: strength = score × confidence, halved every `2 + 3 × weight` days; a unit whose estimate falls below 0.3 after one half-life is "decayed" and is drawn again as a candidate (the only way a Known/Automatic unit returns). This is independent of FSRS. |
| Verification | `scheduler/verify.ts`, `test/goreview/scheduler/vectors.json` | Frozen reference vectors computed by the library itself, adapter checked against them, library drift detection, invariants (intervals grow, Hard ≤ Good < Easy, retrievability monotone). 2,000-card / 20,000-review scale scenario; eight learner scenarios with fake clocks. |

What is good and must be kept: the library is used unmodified and provably (vectors); the deck is a deterministic fold, so
every device agrees; grades are honest (no schedule movement from assisted answers); explicit early practice does not move
the schedule; every state and event carries the exact profile it was computed with, so history can be refolded forever.

## 2. Findings

Ranked by how much they cost the learner or the device. "Measured" means this audit's benchmark; everything else is read
from the code.

### F1. The deck is refolded from the whole log three to four times per card (performance; measured)

Every presentation and every answer go through `presentationGuard` (`app/workspace.ts:260`), which reads the **entire**
local log from storage (`ctx.events` → `log.list` → `area.list` + `area.get` of every key, `app/state.ts:275`) and folds the
**whole** deck again, only to look up one item. The runner does the same on its own account: `appendDueReturns` before each
`current()` and `trackTimedReturn` after each answer each read and fold the whole log (`runner.ts:296-335`). The home load adds
`selectReviewEvidenceEvents` passes from `createReviewEligibilityContext`, `microdeckObservations` (called without the shared
context from `deckModel.assemble`), `observedReviewSeconds` and `admissionBudget`.

Measured, fold alone (CPU, excluding the storage read, which is likely the larger cost on a phone):

| History | Events | Log as JSON | One fold | `selectReviewEvidenceEvents` | Eligibility context | `planSession` |
|---|---|---|---|---|---|---|
| 300 cards × 8 reviews | 3,900 | 2.1 MB | 29 ms | 50 ms | 64 ms | 78 ms |
| 1,000 × 10 | 17,000 | 8.8 MB | 141 ms | 199 ms | 240 ms | 304 ms |
| 2,000 × 10 | 42,000 | 20.1 MB | 329 ms | 518 ms | 633 ms | 734 ms |

At 17,000 events a learner pays roughly half a second of CPU per card plus four full log reads, before any exercise is built.
The log only grows: it also holds every GoLearn encounter and lookup (the fold filters by language, not by kind), and nothing
checkpoints the fold. The scale test bounds (15 s) do not catch this because they measure one fold, not a session.

### F2. The documented ranking does not operate (scheduling quality)

`FSRS-2-ARCHITECTURE.md` and `priority-policy.ts` describe a ranking of 45 % forgetting risk, 25 % reading relevance, 15 %
retrieval difficulty, 10 % diversity, 5 % urgency, multiplied by the Knowability stage weight. In `planSession` this score is
only the **tie-breaker** behind due time for the learning and due tiers (`orderQueueCandidates`, `planner.ts:143`), and the
planner never supplies `readingRelevance`, `recentExposure`, `diversity` or `cost` to it (`planner.ts:189`), so those factors
are constants for every card. In practice a batch is "the ten cards that came due earliest", whatever their value. For a
returning learner with a backlog this means the first batches are the longest-overdue cards (lowest retrievability, which is
defensible) but with no relevance to what they are reading now and no diversity across families. The stage weights
(Recognized/Familiar 100, Known 25, Automatic 3) therefore mostly affect the new tier.

### F3. Two forgetting models disagree by construction (consistency)

The Repository's half-life model (`projection.ts`: base 2 days + 3 days per unit of evidence weight, threshold 0.3) decides
when a Known or Automatic word is *proposed again*; FSRS decides when its *card is due*. They are never reconciled: a card can
be comfortably not-due under FSRS while the Repository reports retention 0.2 and raises a `retentionDecayed` candidate, and
the reverse. `KNOWLEDGE-LEVELS.md` itself calls every projection threshold "a hypothesis until calibrated". FSRS already
has a calibrated retrievability for every reviewed card; the half-life model duplicates it with uncalibrated constants.

### F4. Typed answers give FSRS only two grades (scheduling quality)

`ratingFor` turns a typed answer into Again or Good; Hard and Easy exist only for self-grades (`grade.ts:175-193`). A
`partial` (right word, missing ë/ç or vowel points; the lemma instead of the asked form) is **Again**, so it counts as a lapse,
enters relearning and increments `lapses`, although the learner retrieved the word. FSRS-6 is fitted on four grades; feeding it
two wastes the model's resolution and the partial-as-lapse rule overstates difficulty for exactly the learners (Albanian,
Hebrew, Greek) the folds were written for.

### F5. Learning steps are tuned for a desktop flashcard session the app does not have (scheduling quality)

The default steps (`1m`, `10m`) mean a new card answered Good is due again in ten minutes. A default session is ten cards at
15–40 s, about four to six minutes, so the return rarely falls inside it; the card then sits as "due learning" until the next
session, and the home shows it in the learning count. The runner's timed-return machinery (displacement, pending returns across
reloads, three refolds per card) exists largely to serve these steps. FSRS-6 is designed to schedule from the first review
without steps; whether `[]`, `['10m']` or the default serves retention better here is an empirical question (see §3, stage 0).

### F6. Changing desired retention does not reschedule anything (behaviour the learner will not expect)

Due dates are stored on the state at review time (`fromCard`), so moving the Settings slider from 90 % to 80 % changes only
reviews recorded afterwards; the current backlog stays as it was. Not a defect in FSRS terms, but the Settings copy ("Higher
means more reviews") implies an immediate effect. A derived due (computed at read time from stability, last review and the
current retention) would make the slider immediate and would also let the planner spread reviews across days deterministically.

### F7. Personalization is correct but practically unreachable (optimization pipeline)

The gate is sound and the binding is the official one, but the path to it is: export the Repository, run `npx vite-node
scripts/optimize-goreview.mts` on a computer with Node 20+, carry the JSON to the phone, import it under "Advanced memory
personalization". It covers one objective (`written-recognition`) per language, and the fit is called with
`numRelearningSteps: 1` and `enableShortTerm: true` hard-coded (`optimizer.ts:63`) whatever steps the active profile uses.
No learner will do this; the defaults will be the only parameters ever used. The Repository service already has Node and the
export, so the job belongs there.

### F8. The profile applies inconsistently between planning and recording (minor)

`engine.plan` builds its scheduler with the personal profile for **all** items (`engine.ts:174`), so retrievability and
priority of production or listening cards are computed with recognition weights; the runner applies the profile only to
`written-recognition` cards when recording (`runner.ts:213`). Small today (the profile is rarely active), wrong once F7 is fixed.

### F9. Every review event carries the full 21-weight profile (storage)

`normalise` copies the whole `ScheduleProfile` into `payload.schedulerProfile` on every review (`runner.ts:532`): about 400
bytes per review, repeated identically. At 20,000 reviews that is most of the 20 MB log in the table above. The
`parametersVersion` hash already identifies the profile; the profile itself is asserted once as a `PreferenceChanged` event.

### F10. The adaptive batch cannot adapt for most learners (minor)

Both the shrink and the growth rule in `chooseMicrodeckTarget` require latency samples across at least two modalities
(`minModalities: 2`). New and Seen words are recognition-only by policy, so a learner in the first weeks, or one with
recognition as the only goal, never triggers either rule; the target stays at 10.

### F11. The UTC day is the learner's day (minor)

`admissionBudget` counts introductions per UTC day. For the owner's time zone the daily allowance resets at 17:00 local, so an
evening session and the next morning's session share one allowance while two afternoon sessions do not.

### F12. No test measures scheduling quality (verification gap)

The tests prove determinism, library fidelity and bounds, and they are good at it. None asks whether the schedule is any good:
there is no simulated learner with a hidden true forgetting curve, so a change to steps, grades, ordering or retention cannot
be judged except by argument. The optimizer's log-loss/calibration measures exist but are only run on an export by hand.

## 3. Suggested rebuild: "FSRS stays, everything around it gets a measurement, a cache and one retention"

The library, the event log and the fold's guarantees stay. The rebuild is read-side and additive: no event is rewritten, old
clients keep folding, `parametersVersion` identities stay valid. Five stages, each shippable alone, in the order that pays
first.

### Stage 0. A simulator and a backtest, so every later stage is judged by numbers (≈ 3 days)

- A simulated learner: a hidden memory (a per-card true stability drawn from a distribution, noise on recall) answers whatever
  the planner presents; the harness runs N days of sessions under a time budget and reports retention at due, reviews per
  day, days to Known, backlog size, time spent. The current planner is the baseline.
- A backtest over the owner's real export (the optimizer's `reliableReviewHistory` already prepares it): log loss and
  calibration of the default profile, and of each candidate change below where it affects prediction.
- Acceptance for every later stage: not worse on retention at equal time, or less time at equal retention, on both.

### Stage 1. Per-card incremental fold and an in-memory replica (fixes F1; ≈ 4 days)

- Every rule in `foldDeck` is keyed by `subject.cardId` (ordering, convergence, corrections, invalidation, repair). Index the
  log by card once and fold **per card**; cache each card's fold keyed by the set of its event ids. A new event invalidates one
  card. The presentation guard and the runner then refold one card, not the deck: at 17,000 events this is the difference
  between ~140 ms × 4 per card and well under a millisecond.
- Keep one in-memory replica per learner behind the existing lock, watermarked by the log head (`log:head`), refreshed by
  seq after a pull, instead of reading every key from storage on every guard. Keep the full refold as the fallback and as the
  cross-check in tests (the per-card fold must equal the whole fold on every scenario; the scale test already shuffles delivery
  order).
- Compute `selectReviewEvidenceEvents` once per home load and hand the context to `assemble`, `budgetFor` and
  `observedReviewSeconds` (today they recompute).
- Optional checkpoint: persist the per-card folds with the head seq so a cold start replays only what arrived since.

### Stage 2. One retention, four grades, an operative ranking, a derived due (fixes F2–F6, F8; ≈ 6 days, each item gated by stage 0)

- **One retention.** Add `stabilityAfter` and `difficultyAfter` (additive fields) to the review payload at record time; the
  Repository projection computes `retention.estimate` as FSRS retrievability from the card's last reviewed state instead of the
  half-life, and `retentionDecayed` becomes "retrievability below the learner's desired retention". `HALF_LIFE_*` retire; the
  level rules keep their counts and spacing.
- **Four grades for typed answers.** `partial` with a fold-only difference → Hard (retrieved, imperfect); the lemma for an
  asked form → Hard; `incorrect` → Again; `correct` → Good, or Hard when the answer took longer than a per-family threshold
  derived from the learner's own median (`observedReviewSeconds`); Easy stays self-report only. Evaluate in the simulator and
  the backtest before shipping; record the rule version on the event (`gradingPolicyVersion`).
- **Ranking that acts.** Inside the due tier, order by a value per second: forgetting risk (1 − R) × stage weight × relevance
  (the Repository candidate's reading-relevance signal, which exists but is never passed) ÷ estimated seconds, with an overdue
  floor so the oldest cards cannot starve. Keep due time as the order of the learning tier. Pass the signals the policy already
  defines; delete the factors that stay unused after that.
- **Derived due.** Store stability and last review as today; compute `due` at read time as `lastReview + interval(S, desired
  retention)` through the library's own interval function, so the retention slider acts at once. Add deterministic day
  smoothing: an offset of up to ±5 % of the interval hashed from the card id, so two devices still agree and review load does
  not clump on single days (this is what fuzz is for; the hash makes it reproducible).
- **Learning steps.** Run the simulator on `['1m','10m']`, `['10m']` and `[]`. If `[]` is not worse, adopt it for recognition
  families: the timed-return machinery shrinks to a fallback, and the "due learning" count on the home disappears for most
  learners.
- **Profile per objective.** `schedulerFor(item)` in the engine and the runner resolve the profile by dimension, both from the
  same table.

### Stage 3. Personalization that happens by itself, activated by the learner (fixes F7, F9; ≈ 4 days)

- Move the optimizer run to the Repository service as a scheduled job per (learner, language, objective): the gate, the
  chronological hold-out and the official binding stay exactly as they are; the job posts a **candidate** profile assertion
  (`PreferenceChanged`, key `goreview.schedulerProfile.candidate`) with the report attached. The app shows "A personal
  profile predicts your recall better: use it?" with the two numbers; activation stays explicit, one tap. Fit with the active
  profile's actual steps, not a constant.
- Reference profiles by hash: `payload.schedulerProfileRef = parametersVersion`; the fold resolves it through the profile
  assertions in the same log and falls back to the embedded profile on old events. Roughly a 5× smaller review event.
- Lower the per-objective gate only when stage 0's backtest shows the hold-out is still informative; keep 400/50/60 otherwise.

### Stage 4. Batch and day (fixes F10, F11; ≈ 1 day)

- Let the micro-deck shrink or grow on one modality when the sample is large enough (`minFastSamples` × 2), and feed the plan's
  time budget from the learner's measured seconds rather than the constants once ten samples exist.
- Record the local day on each review (`payload.localDay`, additive) and count the new-card budget by it.

### Stage 5. Verification that stays (≈ 2 days, mostly done by stage 0)

- The simulator and backtest run in CI with frozen seeds and report the four numbers; a change that moves retention or time by
  more than a set margin fails.
- The per-card fold equals the whole fold on every scenario and on shuffled delivery.
- The frozen vectors stay the proof that the library is unmodified.

## 4. What the rebuild does not change

- The event log, its contract and every existing event. All new fields are optional; all new behaviour is read-side or opt-in.
- ts-fsrs as the only memory arithmetic; the published defaults as the only parameters until a learner activates a profile.
- Honest grades: assisted, hinted, challenged and revealed answers still never move a schedule.
- Explicit practice before due keeps the schedule; a lapse is a lapse wherever it happens.
- Determinism across devices: the derived due and the day smoothing are pure functions of the state and the card id.

## 5. Order and effort

| Stage | Pays for | Effort | Depends on |
|---|---|---|---|
| 0 Simulator + backtest | judging every other change | 3 d | – |
| 1 Per-card fold, replica, one evidence pass | F1 | 4 d | – |
| 2 One retention, four grades, ranking, derived due, steps | F2–F6, F8 | 6 d | 0 |
| 3 Service-side optimizer, profile refs | F7, F9 | 4 d | 0 (for the gate), service deploy |
| 4 Batch and local day | F10, F11 | 1 d | – |
| 5 CI gates | F12 | 2 d | 0, 1 |

Stage 1 can start today and is the one the learner feels on a phone. Stage 2 is where retention and time improve, and it
should not ship any item the simulator does not vindicate.
